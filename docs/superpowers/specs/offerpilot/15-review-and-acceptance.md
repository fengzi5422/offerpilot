## 1. 先确认的四组决定

这是根据原文提出的可执行草案；以下“推荐”不等于用户已经同意。逐组解释、修改后记录，也可用户一次批准全部推荐项。开发需等范围与相关模块设计确认。

| 组 | 需要确认的决定 | 推荐选项 | 替代方案与影响 | 状态 |
| --- | --- | --- | --- | --- |
| A 架构与范围 | 运行形式、首轮功能、分期 | Windows 本地服务+浏览器+托盘；首轮 P0，AI/看板/日历等 P1 | 原生窗口增加壳依赖；P0+P1 一起开发延长首个可用版本 | P0 已确认 |
| B 解析与隐私 | 哪些结果自动生效，数据如何保存 | 规则默认；模糊时间送审；凭据安全库；保留最小正文证据 | 全部先审核更保守但操作更多；保留全文方便重解析但存储更多隐私数据 | P0 已确认 |
| C 任务与提醒 | 截止精度、改期、通知语义 | 不补 23:59；多动作独立时间；改期确认；Windows+应用内；未知发送不自动重试 | AI 日期自动生效风险更高，不建议；手机通道可提前但要增加服务配置 | P0 已确认 |
| D 体验与交付 | 页面、备份、开发次序 | 五步向导；先任务闭环后邮箱；P0 含备份恢复与安装；自启默认关 | 先对接邮箱可较早接真数据，但增加调试依赖 | P0 已确认 |

需要用户选择的最关键差异：**先完成可靠 P0，再加 AI/看板/日历，还是把其中某项提前？** 其余字段、错误码、事务约束通常可作为整组技术设计批准，无需逐个表字段答复。

## 4. 业务场景与异常验收

| 场景 | 期望/验证方式 |
| --- | --- |
| A1 同邮件三次同步 | 邮件出现位置不重复；预期动作数恒定 |
| A2 一封面试含回复/上传 | 独立动作、独立期限，不共用错误时间 |
| A3 收到后 48 小时 | 展示参照和候选，确认前无定时提醒 |
| A4 改期 | P0 送审且不建第二有效计划；P1 确认更新原任务 |
| A5 广告误判 | 忽略后同步和解析升级不再提示 |
| A6 断网/休眠两天 | 续扫不漏持久化范围，迟到提醒汇总 |
| A7 手动任务 | 无邮箱无网络也可创建、编辑和提醒 |
| A8 AI 超时/余额不足 | 规则继续，原任务与人工字段不丢 |
| A9 关闭与退出 | 关浏览器托盘继续；显式退出停止 |
| A10 通知重试 | 明确失败有限重试，未知结果不自动重发 |

NFR-01 安装见 M14；02 本地可用见 M01/M07；03 同步可靠见 M03；04 幂等见 M02/M08；05 持久化见 M02；06 易用性见 M12；07 安全见 M10；08 诊断见 M14；09 恢复见 M13；10 可访问见 M12。对应每项均须在交付记录标明执行环境、结果和证据。

## 5. 确认后的开发顺序

这是工作包边界，不是已经开始执行的编码计划。每个包在实施前按 writing-plans 拆成具体文件、步骤与验证命令；不提前编写尚未批准的完整实现。

| 工作包 | 交付 | 退出条件 |
| --- | --- | --- |
| W1 环境与本地壳 | Git/依赖锁、目录/日志、数据库、API 会话、最小任务页、通知打包探针 | 独立开发环境；本地任务可保存重启；通知/凭据/托盘风险验证 |
| W2 EML 与规则闭环 | 导入、规范化、分类、时间、证据、审核 | 至少 10 个典型样本和异常端到端 |
| W3 可靠提醒 | 模板、状态、竞争保护、Windows/应用内、恢复 | 修改/完成/重启无重复计划，unknown 可见 |
| W4 QQ 邮箱 | 凭据、只读同步、游标、断线回补 | 模拟故障通过，真实账号连接成功 |
| W5 可用 MVP | 向导、诊断、导出/恢复、托盘、自启、安装包 | P0 场景通过；开始 7 天实测和非技术用户验收 |
| W6 AI，P1 | 可选模型、脱敏、schema、评估 | 故障回退与人工保护；用户单独批准 |
| W7 求职管理，P1 | 聚合看板、改期向导、日历 | 关联/拆分与冲突测试；用户单独批准 |
| W8 扩展接入，P1 | 第二邮箱、一个移动渠道 | 实际服务测试；用户单独批准 |

开发按工作包提交，持续更新实施日志和验收状态。无需为每个内部函数再请求确认；涉及已批准范围、数据发送、运行形态的实质变更再提交具体方案。
