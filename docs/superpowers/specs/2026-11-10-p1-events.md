# P1 事件管理增量设计

日期：2026-11-10。用户实测后指出“能识别时间地点但日期时间无法填入，时区不重要，事件重要”，并选择先完成事件管理。本设计和同日实施计划记录本轮范围，沿用原 PRD/HLD 的本地只读邮件、人工确认与可靠提醒目标。

## 事件录入和审核

表单优先事件名称、类型、日期/时刻、可选结束、地点和会议链接。地区设置折叠，后台继续保存时区，避免提醒时间偏移。日期和时刻输入始终可编辑；仅日期不虚构截止时刻，也不安排提醒。

精确顶层时间直接填入。只有一个候选时预填但保留待确认；缺年份等多候选明确选择，点击同时填入日期与时刻。确认保留原文、候选和时间依据。切换面试/笔试与截止类事件时同步转换 starts_at/due_at，清除不适用的结束时间。

rules-v2 按明确动作和相邻标签归组，保留原文范围作为证据；不同明确动作分别归属日期。支持单日期、同日两个时刻的区间，以及明天/后天/本周或下周指定星期的待确认建议。未知或复杂时间仍送审，不猜测跨日区间。时间解析排除地点、会议链接与 UTC 偏移中的数字。明确“面试地点”可以先于时间出现，不附到之前的回复截止上。

## 数据与兼容

Task.event_details 为 JSON：location（最多 1000 字符）、meeting_url（最多 4096 字符）。链接仅接受无用户信息的 http/https；无效解析链接留空，原文仍作证据，不能因此使整封邮件解析失败。界面只在用户点击时打开链接。

0004_event_details 在 0003_parse_cache 基础添加字段，旧行默认空对象，接口补齐空字符串。数据库升级沿用先迁移副本、保存升级前快照、失败恢复机制。JSON/CSV/备份恢复贯通，CSV 字段保持公式转义；旧 0001/0002/0003 备份先校验可信结构再升级。

## 改期和取消

POST /api/v1/emails/{message_id}/resolve-change 显式提供 candidate_id、task_id、action、expected_version 和 expected_task_version。没有自动选择或模糊合并。界面展示原事件及新时间，用户再次确认；原地点/链接默认保留，可选择同步修改。

服务验证邮件归属、候选 open 且属于变更、原事件 active、双方版本。改期必须确认精确时间且适合原事件类型。取消转换原任务状态，改期修改原记录，任务 ID 不变。数据库活动锁、任务锁、命令事务覆盖任务、提醒重建/撤销、候选关闭、邮件状态、审计和幂等回执。任一步失败整体回滚；已发送系统通知不能撤回。

source 保留原邮件，并追加最近 50 条变更证据供查看。旧版本重新识别不覆盖已保存任务；旧 open 建议由新结果替代，accepted/ignored 决定保留。证据范围变化与 ignored 原动作重叠时不复活；已有 accepted 同类动作的新结果必须关联原事件，防止再次确认生成重复任务/提醒。

## 周日历

GET /api/v1/calendar 接收 start、end（不含）和地区，最多 93 天。按地区午夜筛选 active 任务，包含跨日相交事件；日期未定、仅日期、未确认及未知结束信息保留在返回结果中。周一至周日视图支持上一周、本周、下一周、指定日期跳转和点击编辑。

仅确认的面试/笔试开始时刻参与日程冲突：两个已知区间按半开区间相交判断；未知结束且开始点落入已知区间、或两个未知开始点相同，只提示可能冲突。截止点和仅日期不冒充占用区间。最多返回 500 组冲突，达到上限明示截断。结束未知不假设一小时或任何默认时长。

## 边界

本轮不含 AI、自动申请聚合/看板、第二邮箱或手机通知。复杂、多日期或无明确动作的正文仍需人工补充。P0 真实 QQ 七天、干净 Windows、五名用户和完整可访问性门槛保持待验。本轮不升级或读取用户正在使用的真实邮箱安装；打包和浏览器检查均使用独立虚构数据。
