# OfferPilot Lite 产品需求文档（PRD）

**版本：** V1.0（可执行规划版）  
**日期：** 2026-11-09  
**阶段：** Windows 单机优先 / 小规模真实用户验证  
**目标读者：** 产品设计者、开发者、测试者，以及后续使用 Codex 实施的开发人员  
**配套文档：**《OfferPilot Lite 技术概要设计 V1.0》

> **项目一句话：** 将招聘邮件自动转成可核对的求职事件、待办任务和提醒，帮助应届生减少错过测评、笔试、面试和材料截止时间的风险。

## 1. 项目背景与目标

### 1.1 背景及用户痛点

秋招、春招和实习求职阶段，用户常同时投递多家公司，邮件到达时间不固定、来源分散、通知格式差异大。一封邮件可能是投递确认、在线测评、固定时间笔试、面试改期、资料补交或 Offer 确认。常见困难包括：信息被广告淹没；“48 小时内”之类相对时间难以管理；同一企业多轮邮件不易归档；面试时间冲突；只看邮箱但未形成行动计划；电脑关闭后无法持续提醒。

### 1.2 产品定位

OfferPilot Lite 是一个面向应届生与实习求职者的 **本地优先招聘进度助手**，而非通用邮件客户端或自动投递平台。它把“识别通知 → 生成行动 → 计划时间 → 提醒执行 → 更新进度”形成闭环，允许用户随时手工修正 AI 结果。

### 1.3 核心目标与边界

- **G1 不漏事：** 从指定邮箱中识别重要招聘相关邮件，对高风险或模糊信息明确展示“待确认”。
- **G2 不算错：** 截止时间必须保存原始依据、时区和计算结果，不得在缺乏证据时自动猜测。
- **G3 不重复：** 同一邮件多次同步不重复建任务；改期邮件应更新既有日程或提示合并。
- **G4 容易用：** Windows 用户安装后可通过向导完成邮箱连接、通知测试和首次同步，无需终端命令。
- **G5 用户可控：** 邮箱只读、AI 可关闭、数据默认本地保存、提醒与自动生成内容可以编辑或取消。

**非目标（首版不做）：** 自动投递简历、读取所有附件并执行程序、自动代用户回复企业、替代日历客户端、跨设备实时同步、全天候云端托管、大型 Agent 系统、模型自动打开未知邮件链接。

### 1.4 目标用户

| 用户类型 | 主要场景 | 需要的价值 |
| --- | --- | --- |
| 校园招聘中的应届生 | 多家投递、集中笔面试 | 自动归纳时间、提醒不遗漏 |
| 实习求职者 | 一边学习一边求职 | 今日待办、日历冲突提醒 |
| 技术基础较弱的用户 | 不熟悉 API、数据库和部署 | 一键安装、引导式配置、清晰错误提示 |
| 小规模内测用户 | 少量不同邮箱与设备 | 安全、稳定、容易导入与迁移 |

## 2. 设计原则和产品约束

1. **任务优先于摘要。** 邮件可能值得记录，但不一定需要待办；先判断是否应触发行动。
2. **证据优先于推测。** 对于时间、地点、会议链接等关键字段，保留原文位置/摘录及可信来源。
3. **可纠错优先于全自动。** 自动提取的截止时间允许用户校正；低置信度任务进待审核队列。
4. **本地优先，不等于完全离线。** 已存数据可离线查看；新邮件同步需要联网；远程 LLM 需要用户授权并联网。
5. **诚实告知提醒边界。** 电脑休眠或关机时，本地进程通常无法进行新邮件扫描与即时网络推送；恢复运行后补同步和显示漏提醒。
6. **小步扩展。** 先服务个人，再扩展多邮箱/多用户/手机，不为假想规模预置复杂基础设施。

## 3. 典型用户旅程

### 3.1 首次使用：五步向导

| 步骤 | 用户看到/操作 | 系统应提供的反馈 |
| --- | --- | --- |
| 1. 欢迎页 | 了解“本地保存、只读邮箱、提醒限制” | 明确隐私说明与风险提示 |
| 2. 连接邮箱 | 选择 QQ 邮箱，输入地址及授权码 | 提供图示说明、密码框遮挡、连接测试 |
| 3. 选择解析模式 | 默认规则模式；可选“启用 AI” | 告知网络调用及数据传输范围 |
| 4. 设置通知 | 启用 Windows 通知，点击“发送测试” | 显示系统通知与状态确认 |
| 5. 首次同步 | 选择近 14 / 30 天或从现在开始 | 展示进度、识别结果、待确认项 |

向导完成后直接进入“今日待办”，提供清晰的下一步操作。用户随时可以在设置页重新运行上述步骤。

### 3.2 招聘邮件到达后的流程

1. 系统发现新邮件，先去重并做轻量过滤。
2. 对可能是招聘信息的邮件运行规则解析；启用 AI 时可辅助提取。
3. 系统识别招聘事件类型、公司、岗位、时间、所需动作与链接。
4. 校验结构化结果。可靠且明确的行动自动生成任务；有歧义则放入“待确认”。
5. 将事件关联到公司 / 岗位投递记录，若存在改期/取消，优先更新原任务。
6. 用户在待办、日历或求职看板中查看并处理；提醒到点发送并记录结果。

### 3.3 重要异常旅程

- **账户授权码失效：** 同步状态显示“需重新授权”，旧任务仍可查看和提醒。
- **邮件写“收到后 48 小时”：** 显示计算依据和建议截止时间，默认待确认；不可无提示地选择发送时间替代收件时间。
- **同一面试改期：** 关联旧日程，更新后取消旧提醒，新提醒依照新时间计算；无法确定关联时请求确认。
- **电脑关机两天：** 重启后补同步最近遗漏邮件，显示“已错过/需立即处理”而非静默补发一串过期提醒。
- **AI 不可用或余额不足：** 自动退回规则模式，保留待人工处理队列，不能中断基础提醒。

### 5.1 邮件事件业务语义

必须区分三层对象：**Mail（原始邮件）**、**Recruitment Event（招聘事件）**、**Task（用户要做的动作）**。一封邮件可触发零个、一个或多个事件；一个事件可能产生多个任务，例如“确认面试时间”和“上传作品集”。重复同步只补充数据，不应重复创建相同动作。

| 邮件事件类型 | 默认处理 | 任务示例 |
| --- | --- | --- |
| 投递确认 | 记录申请状态 | 一般不建待办 |
| 在线测评邀请 | 建待办，提取截止 | 完成测评 |
| 固定笔试/面试 | 建日程和提醒 | 参加笔试/面试 |
| 需确认参与 | 建待办 | 在截止前确认出席 |
| 材料补交 | 建待办 | 上传成绩单/作品集 |
| 改期 | 更新日程或待人工合并 | 新时间参加面试 |
| 取消/流程终止 | 变更流程状态，按确认规则取消提醒 | 无新的待办 |
| Offer / 签约 | 建确认事项 | 在约定时间前回复/签约 |
| 广告/职位推荐 | 默认忽略 | 无 |

### 5.2 时间、优先级与提醒规则

- 时间统一保存为 UTC 时刻、原文字符串、来源证据、原始时区和用户显示时区。仅有日期没有具体时刻时，需要显示“日期明确、具体时间未知”，不能默认视为 23:59 的确定截止。
- “明天”“本周五”“48小时内”等相对时间必须确定参考时间与时区；有歧义则进入待确认。默认不在不确定期限上做静默自动排程。
- **推荐优先级：** 固定面试/笔试 ＞ 近期截止测评和材料 ＞ 需回复确认 ＞ 普通进度通知。用户可以覆盖。
- 预设提醒是用户可编辑模板，例如测评截止前 24 小时与 3 小时，面试前 1 天、1 小时和 15 分钟。提醒不能早于任务创建且不得指向已过时刻。
- 安静时段允许延后一般通知，可能错过截止的高优先级事项应明确提示风险并由用户选择策略。
- 系统必须展示“最近一次提醒状态”和“下一次提醒时间”。提醒发送成功不代表用户已经看到，避免标注“已读”。

### 5.3 求职流程状态

建议基础阶段为：`已投递 → 待测评 → 待笔试 → 待面试 → 待结果 → Offer / 已结束`。同一申请可能跳过阶段或倒退，阶段不能被设计为不可逆的硬编码流程。用户能手动改变阶段；AI 只给出建议。每次状态变化记录来源（邮件、手动、系统）。

### 5.4 数据隐私与用户控制

- 邮箱默认**只读获取**，产品不删除、不归档、不发送邮件，不索取主账号密码。
- 授权码存放在操作系统安全凭据存储中；本地数据库优先只保留邮件元数据、必要正文片段及任务证据，不默认保存全部附件。
- 外部 AI **默认关闭**；启用前告知会向配置的模型服务发送哪些文本、如何遮盖不必要的个人信息。即使用户启用 AI，也不向模型提交邮箱授权码。
- 支持暂停监听、移除邮箱、删除本地邮件缓存、导出/删除个人数据，并说明操作后对既有任务的影响。
- 日志中不应出现授权码、完整邮件正文、面试链接中的敏感 Token 等信息。

## 6. 非功能需求（NFR）

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |
| NFR-01 易安装 | Windows 10/11 为首个目标；安装包运行后无需配置 Python、Node 或 Docker | 全新普通用户环境安装演练 |

| NFR-04 幂等可靠 | 同一邮件重复轮询不会重复创建事件与提醒 | 同 UID、重复 MIME、改期邮件用例 |
| NFR-05 任务可靠 | 应用退出后所有任务、阶段和提醒记录仍存在 | 重启一致性检查 |
| NFR-06 简单可理解 | 新用户在图形界面引导下可完成连接与通知测试 | 5 名非开发用户观察测试 |
| NFR-07 安全最小化 | 只监听 loopback、本地 API 无开放跨域、凭据安全存储 | 本地网络暴露与日志审计 |
| NFR-08 可诊断 | 对常见失败给出“原因 + 下一步”提示，不只显示异常栈 | 故障注入测试 |
| NFR-09 可恢复 | 本地数据升级前备份；迁移失败回滚；手工恢复可操作 | 版本升级与回滚测试 |
| NFR-10 可访问 | 文字易读、按钮尺寸适中、状态不只靠颜色区分 | 键盘与缩放检查 |

## 7. 关键业务验收场景

| 场景 | 输入/操作 | 期望结果 |
| --- | --- | --- |
| A1 重复邮件 | 对同一邮箱文件夹执行三次同步 | 只有一条邮件记录及应有的任务 |
| A2 多动作邮件 | 面试邀请要求先回复并上传材料 | 可得到两个独立待办或可编辑建议 |
| A3 相对期限 | 邮件写“收到后48小时内” | 显示时间依据并待确认，不给出未经验证的绝对截止 |
| A4 改期 | 原面试由周三改为周四 | 不会同时存在两个有效的面试提醒 |
| A5 误判 | 广告被识别成笔试 | 用户可忽略并反馈，下次不重复提示 |
| A6 断网 | 两天未联网后恢复 | 可补同步且保留遗漏提示，不弹出大量无效提醒 |
| A7 手动任务 | 用户手动创建“准备项目复盘” | 可脱离邮件工作，提醒正常 |
| A8 AI 失败 | AI 服务超时/无余额 | 规则识别继续、错误可查看、待办数据不丢失 |
| A9 关闭软件 | 用户点击关闭窗口 | 如选择“后台运行”，托盘保持同步；显式退出后明确停止 |
| A10 重复发送 | 通知服务短暂报错后重试 | 不因简单重试造成同一渠道无控制地重复提醒 |

### 8.1 建议的能力演进路线

- **识别演进：** 规则关键词 → 可配置模板 → LLM 结构化补充 → 反馈样本评估。复杂 Agent 仅在需要多步计划、且稳定性得到证明后考虑。
- **运行演进：** Windows 常驻程序 → 托盘与开机自启 → 可选专用常开设备 → 经用户选择的远程托管。不要把纯本地提醒描述为 24/7 无条件可靠。
- **存储演进：** 单用户 SQLite → 数据访问层隔离 → PostgreSQL / 多用户服务（必要时）。先建立账户 ID、事件 ID、幂等键，为将来迁移准备。
- **接口演进：** IMAP Adapter → 163/126 → Gmail/Outlook OAuth/Push；Notification Adapter → Windows → 可用的手机渠道 → 后续合规平台。
- **交付演进：** 安装包和内置本地网页 → 界面完善 → 可选桌面容器 / 手机伴侣 App。

## 9. 风险、假设与应对

| 风险 | 影响 | 缓解办法 |
| --- | --- | --- |
| 邮箱平台限制或认证变动 | 无法登录或同步延迟 | 多适配器、错误引导、同步健康检查、保留手动导入 |
| AI 错误识别日期 | 错过真正截止时间 | 证据字段、确定性校验、待确认、不默认编造 |
| 本地机器睡眠或退出 | 不能持续监听、发通知 | 显示工作状态、开机自启可选、醒来补同步、后续可选手机/常开端 |
| QQ 机器人主动推送限制 | 提醒失效 | 不作为首版唯一渠道，仅做实验性插件 |
| 授权码或隐私泄露 | 个人信息风险 | 系统凭据库、权限最小化、日志脱敏、备份排除凭据 |
| 用户误解“已提醒” | 认为通知等于完成任务 | 区分“已发送/发送失败/已完成”，不显示未经验证的已读 |
| 软件误报太多 | 用户关闭提醒 | 过滤、待审核、误判反馈、通知节流 |

## 10. 验收指标与测试计划

第一阶段不追求“模型准确率”单项指标，而优先测试可靠性与可纠错性。数据集建议至少包含 100 封**已脱敏且获得使用许可**的样本，覆盖：投递确认、测评、固定考试、改期、资料补交、Offer、广告、取消、模糊日期、转发邮件、乱码和时区差异。

- **重要招聘事件召回率目标：** ≥ 95%（作为阶段性测试目标，非上线保证）。
- **明确时间提取准确率目标：** ≥ 95%（仅统计具有无歧义标准答案的样本）。
- **重复任务：** 对重复扫描的幂等用例必须为 0。
- **通知可追踪：** 每条提醒存在计划时间、发送尝试、结果与失败原因记录。
- **可恢复性：** 重启不丢任务；网络中断后补同步；备份可恢复。
- **可用性：** 至少 5 名非开发用户能不使用命令行完成邮箱与通知配置。

### 11.1 需要坚持的产品决策

**首版只有“协助理解与提醒”，不对外自动执行求职动作。** 产品成功的衡量标准不是 AI 调用次数，而是“用户知道今天该做什么，且没有因为软件问题错过重要通知”。
